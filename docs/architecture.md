# Архитектура · автономное Android-приложение

v2.0, proposed implementation. Заменяет desktop-архитектуру v1; требования
FR-06–13 и бизнес-схема сообщений сохранены. Источники API — AND-* в реестре.

## Контур

```text
React UI / локальные assets в Capacitor WebView
       │ submit / статус попытки, узкий typed bridge
       ▼
MarathonNative (Kotlin) — проверка / PIN / одна очередь операций
       │ transaction → commit → ACK
       ▼
SQLite в приватных app data (не cache и не USB)
       │ короткий maintenance → закрытый согласованный snapshot
       ├─ локальная проверенная backup-копия
       └─ operator-authorized страницы snapshot → ExcelJS → native staging
                                              → локальный ZIP + manifest
                                              → SAF create document на USB
                                              → обратное чтение / SHA-256
```

Нет сети, HTTP backend, внешней БД, аккаунтов и прямого соединения с LED.
Локальный origin оболочки не является сетевым сервером на площадке.

## Владение состоянием и границы

UI хранит в памяти только текущую форму, локаль, дистанцию, курсор, экран и ID
попытки. Не писать форму в URL, localStorage, IndexedDB, savedInstanceState,
clipboard или analytics. После reset/нового visitor очищать всё. После перезапуска
незавершённая форма не восстанавливается; уже committed запись остаётся в БД.

Native хранит device_id, app/schema version, PIN hash/session, валидатор, таймеры
операций, SQLite, snapshots и staging. Путь БД — app-specific private storage;
не папка APK, не external cache. Application ID и ключ подписи стабильны. Один
repository/connection owner в процессе, без второй БД в background service.

Native не экспортирует общий executeSql, readFile, shell или произвольный путь.
Операторские методы проверяют PIN-сессию на каждом вызове и в callback системного
диалога. JS validation — UX, native validation — окончательная проверка.
Shared TS и Kotlin правила проверяются одним набором test vectors; совпадение
Unicode/phone/hash не предполагается без тестов.

Ручная модерация принадлежит Excel и не синхронизируется назад. Нельзя показывать
в приложении «одобрено N», опираясь на старую сырую БД.

## Отправка / потерянный ответ

1. UI валидирует форму, создаёт UUID, фиксирует payload, блокирует повтор/редактирование.
2. Native проверяет разрешённую origin/метод, типы, enum, строки/лимиты и режим работы.
   Время/device_id/filter version устанавливает сам, не доверяет UI.
3. По message_id: существующий тот же канонический payload → тот же ACK;
   иной payload → ID_CONFLICT, без UPDATE/REPLACE. Новый ID → проверка словаря,
   insert и commit одной транзакцией. ACK только после успешного завершения.
4. При потере ACK UI не создаёт новый ID. `getSubmissionStatus` отдаёт только
   результат/время, не payload. Результат NOT_FOUND не достаточен, если операция
   ещё в native-очереди: serial owner сообщает PENDING до её завершения.
5. Retry доставляет тот же ID/payload. UNKNOWN не превращается в success.
   При окончательном отказе — ошибка, сохранённые записи не затрагиваются.

Дедупликация одного запроса не является запретом нескольких независимых посланий
с одного телефона. После process death вручную повторённый ввод — новое послание.
Не обещать идентификацию человека без регистрации.

## БД и durable-конфигурация

Для одного киоска с редкими insert предлагается **journal_mode=DELETE,
synchronous=EXTRA, foreign_keys=ON, busy_timeout=5000**, WAL выключен. Это решение
для упрощения тестируемого закрытого snapshot, а не требование заказчика или
универсальное превосходство DELETE. Для rollback DELETE используется EXTRA: это дополнительная к FULL синхронизация
каталога после удаления journal (AND-07), существенная при внезапном отключении
питания. Конкретный native connection должен прочитать и зафиксировать реальный
режим, не понижать его молча при несовместимости. Не выполнять PRAGMA смены журнала внутри transaction.

`specs/schema.sql` — переносимый reference script. В SQLiteOpenHelper `onCreate`
перенести только DDL/seed в уже контролируемую платформой транзакцию; не запускать
скрипт целиком с вложенным BEGIN. PRAGMA настроить в соответствующих lifecycle
методах; проверить каждый открытый connection. Не «чинить» БД пересозданием.

Новый пустой каталог допускает создание схемы. Ошибка открытия ожидаемой БД,
FULL/READONLY/длительный BUSY/corruption → pause collection с диагностическим кодом.
Никакой замены памятью, удаления или нового пустого файла поверх проблемного.

## Snapshot и backup без выдуманного Android API

Нативная публичная обёртка Android SQLite не получает desktop online-backup API
автоматически. В этом проекте используем **кратко закрытый снимок**, не копирование
работающего `.db`.

Один serial executor блокирует новые записи, дожидается окончания принятой
транзакции, закрывает курсоры/statement/все connections. Проверяет, что выбранный
DELETE journal завершён и нет незавершённого journal/WAL. Копирует БД в приватный
snapshot.partial, закрывает и синхронизирует файл; открывает read-only копию,
проверяет integrity_check, count и ID. Только валидный снимок получает постоянное
имя. В finally открыть исходную БД и вернуть сбор; если reopen не удался — pause.
Нельзя держать прием заблокированным на всё время USB-диалога.

Периодическая копия предлагается каждые 5 минут **между пользовательскими
сессиями**. При непрерывной форме — перенести до success/reset, показывать оператору
возраст последней копии; не обещать работу таймера после убийства процесса Android.
Не ставить background service/WorkManager ради точного пяти-минутного интервала.
Локальный last-good не перезаписывается до проверки нового. Политика retention
согласуется; основная БД никогда автоматически не очищается.

Внешняя резервная копия — отдельный ZIP из проверенного snapshot SQLite и metadata
через SAF. Содержит телефоны, нужен ответственный получатель. Копия в той же памяти
не защищает от удаления приложения/clear data/поломки устройства.

Восстановление сначала в отдельную тестовую среду/временный путь после чтения
копии через SAF. Проверить версии, hash, integrity и ID. Не добавлять публичную
кнопку восстановления или reset; производственное восстановление — процедура
разработчика с сохранением текущих файлов, не автоматическая замена на старое.

## XLSX и перенос на USB

Рабочий контракт колонок не изменён. `beginExport` после PIN создаёт snapshot и
фиксирует snapshotId/batchId/counts; native выдаёт страницы с лимитом и только
с актуальной operator capability. ExcelJS работает локально, формирует
all/10/21/42.xlsx и moderation.xlsx. Выдавать данные UI разрешено только пока
на экране сервисный режим, после завершения очистить буферы из памяти.

Native staging принимает только whitelisted имена/индексы binary chunks с лимитом
размера, считает SHA-256, не принимает произвольные filesystem paths. manifest
включает schema/app version, counts по дистанциям, размер/hash каждого файла.
XLSX строки не являются формулами/hyperlink, телефон — строка.

Далее native собирает **один локально проверенный ZIP**, закрывает его, открывает
SAF `ACTION_CREATE_DOCUMENT` с MIME `application/zip` и уникальным именем.
Менеджер выбирает флешку. Путь — URI `content://`, писать через ContentResolver,
не через `fs`, путь `/sdcard` или browser download.

После записи закрыть поток, выполнить доступную синхронизацию дескриптора,
открыть созданный URI для чтения, сравнить size и SHA-256 с staging. Только тогда
показать «Выгрузка сохранена и проверена». Затем менеджер безопасно извлекает
носитель по инструкции поставщика и открывает комплект на другом компьютере.
Read-back не гарантирует защиту от последующего физического повреждения носителя.

На SAF **нет гарантированной atomic rename**. При cancel/отключении USB/обрыве/
потере activity/callback сообщить NOT_VERIFIED; возможный неполный документ
отметить как непригодный, не удалять чужие файлы. БД и last-good staging целы,
повтор — новый файл. Не показывать успех потому, что выбран URI или закрыт диалог.
`export-manifest.status=complete` описывает локальный комплект; отдельно native
хранит результат подтверждения внешней записи. Cancel не считается успешной выгрузкой.

## Android lifecycle и оператор

`onPause`/activity recreation не отменяют уже начатый native commit. UI в фоне
не принимает новых сообщений, чувствительный экран скрывается. При возвращении
из SAF сбросить UI в операторский результат, затем запереть сервисный режим;
потерянная сессия требует PIN. State операции хранить без payload в UI restore.

PIN задаётся при подготовке локально (без default в Git); salted slow hash,
rate limit, не более необходимого времени сессии. Idle lock 60 сек не должен
обрывать физическую запись файла; операция одноразово авторизована, новые
чтения/экспорты после истечения токена запрещены, callback всё равно проверяет
связь с исходной операцией. Потеря процесса → незавершённая операция, не success.

Флаг keep screen on только на переднем плане. После перезапуска менеджер
запускает приложение по инструкции. Автозапуск/полный lock task — конфигурация
поставщика, не обещание обычного fullscreen APK. SAF и lock task проверяются
совместно: может понадобиться разрешённый DocumentsUI или временный выход
оператором. Не обходить блокировки производителя root/accessibility хаками.

## Безопасность APK / личные данные

Release без server.url, live reload, внешних запросов/окошек/navigation, отладочных
инструментов, аналитики, шрифтов из сети и native HTTP. CSP ограничен собственным
origin; локальные assets импортируются в bundle. Не указывать connect-src 'none'
вслепую, если выбранный local asset pipeline требует 'self'; проверить отсутствие
любых удалённых обращений и холодный запуск. INTERNET permission удалить из
merged release manifest при совместимости выбранного shell; это отдельный тест,
не повод включить сеть для приложения. Debug config не попадает в release.

Auto Backup и перенос данных между устройствами исключить явными правилами для
поддерживаемых Android версий, проверить merged manifest и OEM поведение. В папку
cache не класть единственную копию. Данные в приватном sandbox не равны шифрованию.
Для демо и production разные applicationId/data directories; релизный ключ
сохранить у владельца вне Git. Обновления тем же ID/ключом проверить на тестовой
базе. Uninstall, clear data, factory reset запрещены как способ починки на Expo.

Логи содержат только коды, время, versions, operationId и counts. Не логировать
SQL args/payload/PIN/телефоны/пожелания. Скриншоты — synthetic. Runtime не хранит
платёжных данных и не интегрируется с Kaspi QR/Red+, хотя эти бренды есть в PDF.
